# Managed runtime contract

Phase 2b runs local inference outside the API process. The API process does
not import torch, transformers, onnxruntime or llama.cpp bindings. Model
weights are never downloaded by this feature: users place them manually under
`data/models`.

## Catalog and profiles

`GET /api/models/runtimes/catalog` returns the code-owned catalog. Each entry
has a pinned version, platform/architecture, HTTPS artifact URL, SHA-256,
archive format, executable, supported model kinds and a strict options schema.
The first enabled variants are `llama-server/cpu` and
`python-worker/torch-cpu` on x86_64 Windows and Linux. CUDA, Vulkan,
`torch-cu128` and `onnx-gpu` remain visible as unsupported entries until a
platform-specific implementation is enabled.

Managed model profiles set `runtime_id`, `runtime_variant` and validated
`runtime_options`; `provider_profile_id` must be empty. Llama server profiles
are `llm` profiles whose `model_ref` is a safe relative GGUF path. Python
worker profiles are embedding, reranker, image embedding or vision profiles
whose `model_ref` is a safe relative model directory. No profile can provide
an arbitrary executable or command-line option.

The supported llama options are `threads`, `context_size`, `batch_size` and
`gpu_layers`. CPU profiles require zero GPU layers. Worker options are
`device=cpu`, `intraop_threads` and `max_batch_size`. A managed profile is
accepted by CRUD before its runtime or model is installed; execution reports
the actionable runtime/model error.

## Installation

`POST /api/models/runtimes/{runtime_id}/{variant}/install` creates an
installation job. A single application-wide job may run at a time. Archives
are streamed to `data/runtimes/.staging/{job_id}`, checked against the pinned
SHA-256, safely extracted, given an installation manifest, and promoted to:

```text
data/runtimes/llama-server/<version>/<variant>/
data/runtimes/py/<variant>/<version>/
```

The Python worker uses the application `uv` executable only to install the
pinned Python version into the runtime-owned directory, create its venv and
install a hash-locked requirements file. `--no-bin` and `--no-registry` keep
that interpreter out of user PATH and registry. PyPI, PyTorch and GitHub
proxy settings are optional runtime download settings; they never select or
download model weights.

Jobs expose queued/running/completed/failed/cancelled/interrupted states,
stage, byte progress, error code and a bounded log. Cancellation stops the
subprocess and removes staging. A restart marks unfinished jobs and
installations interrupted and removes their owned staging directory. Failed
or cancelled attempts keep their log and can be retried with a new job.
Uninstall stops managed processes, removes only the matching runtime directory
and marks its installation `not_installed`.

## Processes and RPC

Managed processes bind to `127.0.0.1` on a dynamically reserved port. The
supervisor creates a process group and, on Windows, a kill-on-job-close Job
Object. It stops the full process tree on unload, cancellation or application
exit. Stdout/stderr are written to `data/logs/runtimes`, sanitized and capped
at 10 MiB; the latest 20 terminal task logs and 20 process logs per runtime are retained.

`llama-server` is called through the existing OpenAI-compatible adapter. Its
API key is generated per process and stored only in a private process
directory. Python workers expose only these token-authenticated endpoints:

```text
GET  /health
POST /load
POST /unload
POST /embed
POST /rerank
POST /image-embed
POST /vision
```

The worker validates every request with the standard library before importing
heavy engines. It sets `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1`, uses
`local_files_only`, rejects unsafe paths and image data outside bounded data
URLs, and returns only strict JSON result shapes. CPU implementations cover
transformers text embeddings, sequence-classification reranking, CLIP,
SigLIP2, DINOv2, Florence2 and WD14 according to the selected profile. Use
Transformers-native checkpoints; arbitrary remote model code is not executed.
Text embeddings use attention-mask mean pooling with a 512-token limit.
Rerank requires a trained sequence-classification head. WD14 requires
`model.onnx` and `selected_tags.csv`; it does not require `config.json`.
Installation integrity covers the dependency lock, worker source fingerprint
and the complete installed file list, excluding generated bytecode caches.

## Status and API

`GET /api/models/runtimes`, the per-runtime status route and
`GET /api/models/runtimes/jobs/{job_id}` are read-only. Job logs are returned
by the matching log route; process logs are available from a managed profile's
`/api/models/profiles/{profile_id}/log` route. API responses omit absolute
paths, ports, process tokens and raw provider errors.

Managed model status retains the common state/residency/occupancy fields and
adds a runtime object containing runtime id, variant, version, installation
state, process state and latest job id. The common errors are
`RUNTIME_NOT_INSTALLED`, `RUNTIME_INSTALLING`, `RUNTIME_BROKEN`,
`RUNTIME_UNSUPPORTED`, `MODEL_NOT_FOUND`, `MODEL_BUSY` and
`MODEL_UNAVAILABLE`. Runtime job and installation updates are broadcast as
`runtime_job_updated` and `runtime_status` events with an empty session id;
they do not create chat or run rows.
