# Internal Image Generation Contract

This contract owns project-native image generation profiles, internal model
inventory, generation runtime behavior, the Image Generation Capability, and
drawing Agent workflow. It is separate from ComfyUI integration and from the
external stateless inference service.

## Scope

The current internal service supports Image Model Profiles, local model
inventory, fake-backed `txt2img` generation, and internal queue/cancel/cache
governance through a trusted Capability and form-driven Script Agent. It does
not load real model weights, expose slash commands, or expose `/v1` image
generation routes.

The first runtime target is `txt2img` for common Stable Diffusion-style local
checkpoints:

- SD 1.5 family through `architecture=sd15`.
- SDXL family through `architecture=sdxl`.
- Pony, Illustrious, and NoobAI as SDXL variants.
- `z_image` as a reserved architecture adapter for a later round.

Deferred features include img2img, inpaint, video, Flux, arbitrary ComfyUI node
graphs, prompt beautification, preset storage, real model loading, real LoRA
loading, and natural-language-to-structured generation.

## Internal API

Profile APIs:

- `GET /api/image-generation/status`
- `GET/POST/PATCH/DELETE /api/image-generation/model-profiles`
- `GET /api/image-generation/model-profiles/{profile_id_or_alias}`

Inventory API:

- `GET /api/image-generation/model-inventory?kind=checkpoint|vae|lora`

Runtime governance API:

- `POST /api/image-generation/unload`

These routes are workbench-internal APIs. They are not external stateless
inference endpoints and do not use the `/api/inference` or `/v1` route space.
The unload route exists for trusted project UI such as Settings and must not be
treated as an external image generation service.

## Profile Taxonomy

`ImageModelProfile` is the only profile type in this domain. There is no
separate `ImageGenerationProfile`; generation mode is a backend task type.
The current task set is only `supported_tasks=["txt2img"]`.

Fields:

- `id`, `alias`, `name`, `description`, `notes`, `enabled`.
- `architecture`: `sd15`, `sdxl`, or `z_image`.
- `variant`: `base`, `pony`, `illustrious`, `noobai`, or `custom`.
- `checkpoint_ref`: required safe ref.
- `vae_ref`: optional safe ref.
- `dtype`: `auto`, `fp16`, `bf16`, or `fp32`.
- `device`: `auto`, `cuda`, or `cpu`.
- optional positive `clip_skip`.
- `supported_tasks`, compact `metadata`, timestamps.

`pony`, `illustrious`, and `noobai` require `architecture=sdxl`. Other variant
and architecture combinations are allowed so users can represent local custom
models without adding new schema fields.

The profile does not include default checkpoint profile ids, checkpoint
override flags, LoRA override flags, or per-mode public generation profiles.
LoRAs are structured generation request parameters, not Profile rows.

## Txt2Img Request

The internal `txt2img` request is structured data, not a parsed command string.
Fields are:

- `profile_id_or_alias`.
- `positive_prompt` and optional `negative_prompt`.
- `width`, `height`, `steps`, `cfg`, `sampler`, `scheduler`, `seed`,
  and `batch_size`.
- Optional `loras`: list of `{ref, weight}` values.

The service validates profile existence, `enabled=true`, `txt2img` support,
non-empty prompt, dimensions that are multiples of 8, bounded sampler settings,
seed range, batch size, and LoRA safe refs under
`image_generation/loras/...`. LoRA refs are validated only; fake generation and
the first real runtime adapter do not need to load LoRAs until that is
explicitly added.

## Safe Refs And Inventory

Image generation model files live under:

- `data/models/image_generation/checkpoints`
- `data/models/image_generation/vae`
- `data/models/image_generation/loras`

Public refs use POSIX-style safe relative paths:

- `image_generation/checkpoints/<name>`
- `image_generation/vae/<name>`
- `image_generation/loras/<name>`

Refs must not be empty, absolute, contain backslashes, traversal, `.` segments,
or empty path segments. APIs return safe refs and compact relative paths only;
they never return absolute local paths.

Deleting an Image Model Profile deletes only the database row. It must not
delete checkpoints, VAEs, LoRAs, attachments, sessions, settings, Knowledge
data, or user assets.

## Runtime Boundary

The runtime is an internal project service before any external service is
exposed. The current backend is `fake` with `real_generation=false`; it creates
deterministic PNG bytes from stdlib code and does not read checkpoints, VAEs, or
LoRAs.

`txt2img` execution is queued by the internal service with
`max_concurrent=1` by default. Queue state is process memory only and may track
request status as `queued`, `running`, `cancelling`, `completed`, `failed`, or
`cancelled`. Queue status may expose request id, run id, profile id/alias,
task, timestamps, wait/execution durations, and compact request summaries. It
must not expose raw prompts, generated bytes/base64, absolute paths, or LoRA
refs.

`txt2img` Capability results may contain transient `data_base64` image payloads
so the calling Agent can save attachments. Transient bytes/base64 must not be
persisted into Message or Run metadata. Persisted metadata may include compact
request summaries, prompt character counts, prompt hashes, profile ids/aliases,
backend name, request id, queue timing, output count, and attachment ids.

The form Agent creates Runs through the normal Agent runner, writes meaningful
RunSteps, saves generated images as local attachments, and returns image media
groups. Script Agent cancellation uses the normal Run cancel path; cancelled
image generation must not create partial output attachments. Runtime cache
release is best-effort, process-local, and must never delete model files or
attachments.

Runtime implementations may learn from ComfyUI's graph execution and memory
management, but must not expose a user-editable node graph as the first project
API. They should accept structured request data similar to a conventional
txt2img request.

Automated tests should remain fake-backed until real local smoke tests are
explicitly requested. Real runtime dependencies should be optional and must not
inflate the default install.

## Settings UI Workflow

Settings -> Models includes an `Image Generation Models` subsection for
managing `ImageModelProfile` rows. Supported deep links include
`/settings?tab=models&subsection=image-generation-models`,
`image-generation-model-profiles`, `txt2img-models`, and
`image_generation_models`.

The Settings form may create, edit, and delete profiles. It owns profile
fields such as name, alias, enabled state, checkpoint ref, optional VAE ref,
architecture, variant, dtype, device, clip skip, notes, and compact metadata
JSON. `supported_tasks` is displayed as read-only `txt2img`; users must not edit
task types from Settings.

Checkpoint and VAE fields use inventory dropdowns and display only safe refs.
Absolute paths must not be shown. LoRA inventory may be typed in the frontend
client for later generation request parameters, but LoRA remains outside the
Profile table and outside the Settings profile form.

The UI mirrors backend taxonomy rules for fast feedback: selecting `pony`,
`illustrious`, or `noobai` forces `architecture=sdxl`, and changing away from
`sdxl` resets those variants to `base`. Backend validation remains the source
of truth.

Settings may show lightweight runtime status from
`GET /api/image-generation/status`: backend, `real_generation`, profile counts,
queue active/queued counts, and cache summary. It should make the current
`backend=fake` and `real_generation=false` state visible so users do not infer
that real model inference is already connected.

Settings may call `POST /api/image-generation/unload` to release process-local
runtime cache. Busy/not-found/skipped/freed results are displayed as compact
status and must never delete model files. Settings does not launch txt2img,
collect prompts, save generation presets, or return image attachments.

## Capability And Agent

The `image_generation` Capability is for trusted Agent and Script Agent calls.
It exposes no slash commands. Current methods are:

- `status`
- `list_model_profiles`
- `validate_txt2img`
- `txt2img`
- `queue_status`
- `cancel`
- `unload`

The built-in `image_generator` Script Agent is the default drawing entry point,
but it does not automatically replace existing session defaults. Its
`default`/`form` actions show a structured text-to-image form. If the user sends
plain text to `@image_generator`, that text is only used as the initial positive
prompt. The non-callable `generate_from_form` action is reserved for trusted
form submission.

The Agent saves generated images as local image attachments and returns a
`media_group` response. Message and Run metadata must stay compact and must not
contain raw prompts, generated image bytes/base64, absolute filesystem paths, or
LoRA refs.

`queue_status`, `cancel`, and `unload` are internal governance methods for
trusted Agents and later UI plumbing. They are not slash commands. `unload`
returns `busy` when active or queued image generation work would be affected.

A later natural-language drawing Agent may translate user text into structured
generation parameters, ideally with user confirmation before GPU generation.

## External Inference Boundary

No `/v1/images`, `/api/inference/images`, or OpenAI-compatible image generation
route exists. Any future external stateless image generation service must update
`stateless-inference.md` and must keep the existing stateless data boundary
explicit.

## Optional Dependencies

The default install must not require real image generation dependencies. The
optional `image-generation` extra is reserved for later real adapters and may
include non-torch packages such as `diffusers`, `safetensors`, and `Pillow`.
Torch and torchvision remain owned by the existing `knowledge` or
`knowledge-cuda128` installation modes.
